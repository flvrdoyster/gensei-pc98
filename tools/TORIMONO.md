# 환세포물장 역공학 노트

**대상**: 환세포물장 / 幻世捕物帳 (Compile, 1996, PC-98)  
**상태**: 완료  
**도구**: `torimono_parser.py` (추출) · `torimono_inserter.py` (재삽입)

---

## 개요

### 파일 구성

**HDI 이미지 1장** — 시리즈에서 유일하게 FDI가 아니라 부팅 가능한 PC-98 HDD 이미지를
쓴다(DISK_C 그래픽이 2HD 플로피 용량을 넘어서다, 상세는 아래 "5. 재삽입" 참조).
`original/torimono/`에 그 안의 파일을 개별로 추출해 둔다.

```
original/torimono/
  GSC.COM         3,984 B   로더 (DISK_*.DAT 로드 + LZ 해제)
  FPLAY.COM      16,138 B   FM 음원 플레이어
  DISK_B.DAT    573,469 B   스크립트·텍스트·그래픽 (95개 청크)
  DISK_C.DAT  1,243,238 B   그래픽 데이터 (SJIS 텍스트는 없으나 이미지 베이크드 일본어 존재 — 아래 "DISK_C.DAT 그래픽 포맷" 참조)
  PLAY1~8.INF     3,193 B   스테이지 맵 데이터 (텍스트 없음)
  SONG.DAT       15,193 B   음악 데이터
```

텍스트 소스는 `DISK_B.DAT` 하나로, 쾌도전과 같은 구성이다. FPLAY.COM·GSC.COM에도 DOS
드라이버/플레이어의 일본어 에러 메시지가 있지만, 쾌도전에서와 같은 이유로 번역 대상이
아니다.

### 패치 대상 파일

`DISK_B.DAT`는 텍스트가 있는 청크(95개 중 일부) 전체를 패치한다. `DISK_C.DAT`는 청크
전체가 아니라 `torimono_inserter.py`의 `DISK_C_EDITS`에 등록된 청크만 이미지로
재삽입하는데, 지금은 청크 31(그래픽)과 47(스탭롤 글자 시트) 두 개뿐이다 — 새로 베이크드
텍스트를 편집하려면 이 dict에 항목을 추가해야 패치 대상에 들어간다. `PLAY1~8.INF`·
`SONG.DAT`·`FPLAY.COM`·`GSC.COM`은 패치하지 않는다.

### DISK_B.DAT 청크 구조

쾌도전과 같다 — `0x000~0x3FF` 4-byte 엔트리 테이블에 `compile_lz` 압축이 쓰인다. 상세는
`KAITOU.md` 참조.

## 작업 흐름

### 1. 압축 해제

쾌도전과 같은 `compile_lz.decompress()`를 재사용한다. 알고리즘 상세는 `KAITOU.md`/
`HUKYOU.md` 참조.

### 2. 제어코드

오피코드 워킹은 `compile_script.walk`를 공유하고, 대부분 `BASE_SPEC`만으로 동작한다.
포물장에서 따로 보강한 건 엔딩 평가 랭크 제목뿐이라 `TORI_SPEC`을 하나 더 뒀다.

**엔딩 평가 랭크 제목 — `63 fb 『…』 63 ff`**: 엔딩 평가(청크 2)의 랭크 제목 13종
(`『名奉行』`·`『大泥棒』`·`『天下御免の風来坊』` 등)은 `63 fb 『…』 63 ff`로 감싸여
있다. `BASE_SPEC` 워커는 `0x63`을 미지 바이트로 봐서 블록 안 누적 텍스트를 버려버리기
때문에(`cur_text=''`, `compile_script.walk` 참조) 제목 줄을 통째로 놓친다(주변 설명문은
정상 캡처된다). `TORI_SPEC`이 `(0x63,0xfb)`와 `(0x63,0xff)`를 직후가 SJIS일 때만
발동하는 마커로 처리해서 제목과 접두 문구를 캡처하게 했다. 이 2바이트 시퀀스는 평가
영역에만 나오는 고유값이라 다른 청크엔 영향이 없다.

### 3. 반각

포물장에서는 반각을 안 쓴다. 텍스트가 전 구간 전각 SJIS이고, 반각 인코딩이 필요한
좁은 슬롯 자체가 없다.

### 4. 파싱

`torimono_parser.py`는 `kaitou_parser.py`의 복제본이다(게임별 파서를 독립적으로 두는
컨벤션). 오피코드 워커(`compile_script.walk`)를 공유하는 부분은 위 "제어코드" 절과
같다.

**NOISE_CHUNKS를 다시 뽑아야 했던 이유**: 쾌도전의 NOISE 목록은 그대로 재사용할 수
없었다 — 타이틀마다 청크 배치가 달라서, 예를 들어 쾌도전에서 노이즈였던 청크 42·44가
포물장에서는 SJIS 밀도 35~46%짜리 텍스트 청크였다. 그래서 포물장은 다음 절차로
따로 식별했다.

1. NOISE 목록을 비우고 전 청크를 일단 통과시켜 예단 없이 전체를 파싱한다.
2. 청크별로 디컴프 SJIS 밀도, 추출된 글자 중 가나/한자 비율, 1글자 라인 비율을 정량
   지표로 본다. 정상 텍스트 청크는 가나/한자 비율이 80~92%였다.
3. 지표가 애매한 회색지대는 추출물을 직접 눈으로 검증했다. 노이즈로 판단한 건 키릴
   문자, 동일한 희귀 한자의 반복, 의미 없는 한자 조합, `ｃ` 반복 같은 것들이었다.
   반대로 적/캐릭터 이름 블록(`ネコタマ`·`シノビ` 등)은 밀도가 낮아도 정상이었다 —
   짧은 텍스트에 스탯 바이너리가 섞여서 밀도가 원래 낮기 때문인데, 밀도 기준만
   믿었으면 이런 블록이 통째로 걸러질 뻔했다.
4. 이렇게 확정한 목록이 `torimono_parser.py`의 `NOISE_CHUNKS`다(단일 소스).

### 5. 재삽입

포물장은 DISK_C(그래픽)가 2HD 플로피 용량을 넘어서, 시리즈에서 유일하게 부팅 가능한
PC-98 HDD 이미지(HDI)로 구동한다(다른 타이틀은 FDI). 베이스는
`emulator/rom/torimono_kr.hdi`로, IPL1 부트코드 + `MS-DOS 6.20` 활성 파티션 + 게임
파일 전체로 구성돼 있다.

`torimono_inserter.py`가 DISK_B 청크를 패치한 뒤 `patch_hdi`로 베이스 HDI에 교체한다.
`pc98disk.py`가 PC-98 파티션 테이블을 해석해서 파티션 안의 FAT 파일을 교체하는 방식이다
(`tools/NOTES.md` 참조). 쾌도전과 달리 CONFIG.SYS가 없어서 EMM386 제거 단계도 필요
없다.

세이브는 다른 타이틀과 같은 IDB 방식을 쓰고, 키는 `torimono_kr.hdi`다(HDI를 통째로
저장한다).

### 6. 빌드 (웹 에뮬레이터)

np2kai 웹빌드의 커맨드라인 확장자 분기에 `.hdi`가 없어서 `arguments`로는 못 물린다.
`torimono.html`이 preRun에서 번들 안 `np2kai.cfg`에 `HDD1FILE`을 주입해 SASI HDD로
마운트한다(페이지 번들의 파일시스템 안에서만 벌어지는 일이라 공유 cfg 원본에는 영향이
없다). 부팅과 게임 기동은 검증을 마쳤다.

## DISK_C.DAT 그래픽 포맷

DISK_C.DAT은 SJIS 텍스트는 없지만, 그래픽에 이미지로 베이크된 일본어가 존재한다(맵
타일 청크 12~21 등에서 육안으로 확인된다). 청크 테이블 구조는 DISK_B와 같다
(`0x000~0x400`, 4바이트 엔트리, `compile_lz` 압축). 총 71청크다.

### 청크 크기별 분류

| 크기(디컴프 후) | 청크 | 용도 |
|---|---|---|
| 32,000 B | 0, 51~70 | 640×400 1bpp 풀스크린. chunk 0=대화창 UI 프레임(단독). 51~70=타이틀 로고 5프레임 애니메이션(각 프레임=연속 4청크=4 bitplane) |
| 168 B | 1 | "cs v1.4" 헤더 + 4바이트×16 팔레트꼴 데이터 — 실제 팔레트는 아닌 것으로 확인됨(로고·스프라이트 어디에도 안 맞음, 용도 불명) |
| 20,480 B | 3 | 미해결 |
| 0 B | 4 | 빈 청크 |
| 40,960 B | 2, 5~50 | 스프라이트/타일 시트 (아래 상세) |

### 40,960바이트 스프라이트 시트 (chunk 2, 5~50)

256타일 × 160바이트/타일 구조다. 타일 하나는 5블록 × 32바이트(블록 하나 = 16행 ×
2바이트, 워드는 `(hi<<8)|lo`, MSB가 좌측 픽셀)로 이뤄진다.

```
p0 = 블록0의 비트  →  그리기 플래그(0=배경/투명, 1=콘텐츠 있음)
p1~p4 = 블록1~4의 비트 → 4비트 팔레트 인덱스 idx = p1 | p2<<1 | p3<<2 | p4<<3  (0~15)
타일 t, 블록 p, 행 ry 워드 오프셋 = t*160 + p*32 + ry*2
타일 그리드: 256타일 = 16열 × 16행 (타일 = tr*16+tc)
```

chunk 47(스탭롤 글자 시트)도 같은 포맷을 쓴다. 16×16 낱글자가 촘촘히 들어 있어서 얼핏
빽빽해 보일 뿐, 디코드 자체엔 문제가 없다 — 스탭롤(엔딩 크레딧) 전용 글자 집합이다.

#### 팔레트

팔레트는 DISK_C가 아니라 DISK_B에 있다. 시그니처는 4바이트×16이고
`data[i+k*4]==k`(k=0~15, 색번호 순차)이면서 나머지 3바이트가 각각 15 이하인 경우를
`[색번호, R, G, B]`(4비트, ×17로 8비트로 변환)로 본다. DISK_B 전체에 46개 인스턴스가
있고 중복을 제거하면 고유 16개가 남는다. 가장 흔한 팔레트(15곳에서 중복, 예: DISK_B
chunk93 offset 3319)가 대부분의 캐릭터/오브젝트 청크에 적용된다.

```python
PAL0 = [(0,0,0),(153,170,204),(85,119,136),(0,85,255),(0,17,170),(119,187,153),(51,136,68),
        (255,187,153),(221,136,102),(255,0,0),(136,68,34),(255,238,0),(187,170,17),
        (255,221,204),(255,119,187),(255,255,255)]
```

이 팔레트는 실제 게임 캡처(`original/img/face-tamamo.png`, 청크32 얼굴 스프라이트)와
픽셀 단위로 완전히 일치하는 걸로 검증했다.

청크별로 어느 팔레트가 쓰이는지는 `original/img/chunks_pal0/`에 렌더해 저장해 두고
육안으로 전 청크를 확정했다. PAL0은 chunk 2, 5~44, 47(아이템 아이콘·건물/방
인테리어·마을·던전 맵 타일·캐릭터 워크사이클·NPC·이펙트·스탭롤(47) 글리프 등)에
쓰이고, 맵 타일 청크에서 이미지 베이크드 일본어가 확인됐다. 16종 고유 팔레트 중
인덱스 3은 chunk 45(부유섬 배경 일러스트), 인덱스 4는 chunk 46(같은 배경의 다른
팔레트 버전), 인덱스 8은 chunk 48·49·50(캐릭터 초상 일러스트의 표정 변형)에 쓰인다.

#### 타일 배치 인덱스 (2026-07-03 해결)

"글리프가 화면 어디에 그려지는지"를 한동안 DISK_B·DISK_C·GSC.COM 전체에서 찾다가
실패했는데, 구식 포맷을 가정하고 엉뚱한 값을 검색하고 있었던 게 원인이었다. 실제로는
DISK_B chunk 2의 디컴프 오프셋 `0x1d43`부터 폭 19의 타일맵 그리드가 배치 데이터였다 —
각 셀 값이 chunk 47의 타일 인덱스다. 확정한 방법은 슬롯 번호를 타일에 대신 그려넣은
"아틀라스" 테스트판을 만들어 실제 엔딩을 캡처해서 대조하는 것이었다
(`torimono_disk_c.py`로 임시 스크립트를 짜서 세이브 HDI에 삽입한 뒤 캡처 대조).

같은 문구(のみなさん 등)가 여러 화면에서 같은 타일을 공유하는 구조라, 재삽입할 때
타일을 소수 재매핑해야 했다 — 상세와 좌표는 `torimono_inserter.py`의
`STAFFROLL_MAP_EDITS`에 있다.

> **빈 타일이라고 안 쓰는 타일은 아니다.** c47.png에서 픽셀이 비어 보이는 타일도
> 타일맵 어딘가에서 단어 사이 간격 같은 의도적 공백으로 참조되고 있을 수 있다.
> 재매핑용 여유 타일을 고를 땐 이미지가 비었는지만 보지 말고, 타일맵 전체(chunk 2,
> `0x1d43~0x242a`)에서 그 인덱스가 몇 번 참조되는지 직접 세어 0회인 것만 써야 한다.
> 실제로 픽셀만 보고 골랐다가 다른 열(ファーリン)의 공백 타일을 가로채서 그 열에
> 엉뚱한 글자가 붙은 사고가 있었다.

### 재삽입 파이프라인

`tools/torimono_disk_c.py`가 DISK_C 스프라이트/타일 청크의 디코드·인코드·재조립을
전담한다.

```
디코드: p0=0 → 완전 투명(alpha=0) / p0=1 → 팔레트[idx4]색 + 불투명(alpha=255)
인코드: alpha<128 → p0=0 / alpha≥128 → p0=1, RGB를 팔레트에서 최근접 매칭(정확히 일치하면 스냅 불필요)
```

편집할 때는 알파채널로 "그리기 여부"를, RGB로 "16색 중 어느 색"을 지정한다. 팔레트에
없는 색은 자동으로 가장 가까운 색에 스냅된다(이 청크는 16색 고정이라 완전히 새로운
색을 쓸 수는 없다 — 필요하면 DISK_B의 팔레트 자체를 확장/교체해야 하는데 이건 아직
검증 안 됨).

편집용 PNG는 512×512(2배 최근접 확대)로 내보내고, 인코드할 때 2×2 블록 다수결로
다시 축소한다(편집 툴의 안티에일리어싱 등으로 블록이 깨진 곳은 경고를 낸다).

```bash
# 청크를 편집용 PNG로 추출
python3 tools/torimono_disk_c.py decode 31 out.png

# 편집된 PNG를 단독으로 재삽입해 DISK_C.DAT 재조립 (여러 청크 동시 가능)
python3 tools/torimono_disk_c.py encode 31=out.png
```

이 파이프라인은 `torimono_inserter.py`에 정식으로 편입됐다. 편집이 끝난 청크는 상단
`DISK_C_EDITS` 상수(`{청크: PNG 경로}`)에 등록한다. 편집 PNG는
`translation/torimono/graphics/`에 저장하는데, `original/`은 저작권 때문에 gitignore
대상이라 번역 결과물을 거기 두면 유실되기 때문이다. 등록해 두면 `run()` 이후
`build_disk_c()`가 자동으로 `build/torimono/DISK_C.DAT`를 만들고 `patch_hdi()`가
DISK_B와 함께 같은 HDI에 삽입한다 — 웹 에디터의 "빌드" 버튼만 눌러도 둘 다
반영된다. 새 청크를 편집할 땐 PNG를 `translation/torimono/graphics/`에 저장하고
`DISK_C_EDITS`에 한 줄만 추가하면 된다.
