# 환세풍광전 CMD 파서 — 구현 방식 노트

## 배경

**대상 게임**: 환세풍광전 / 幻世風狂伝 (Compile Inc., 1994, PC-98)
**역공학 방법**: 정공법 (GF2.COM 디스어셈블 → 런타임 분석)

---

## 핵심 발견 순서

### 1단계 — 실행파일 압축 확인

GF2.COM을 디스어셈블(`objdump -b binary -m i8086`).
0x100~0x170이 자가 압축 해제 루틴임을 확인.

```
0x12b 루프:
  al = *si++
  if al == 0: 종료
  if al & 0x80: back-reference (length = (al&0x7f)+3, offset = *si++ +1)
  else: literal copy (length = al)
```

Python으로 동일 알고리즘 구현 → 60128바이트로 해제 성공.

### 2단계 — CMD 파일 포맷 파악

압축 해제된 GF2.COM에서:
- `call 0x6f60`: 파일 로드 (INT 21h AH=3Fh)
- `call 0x1417` → `call 0x12f0`: **동일한 LZ 알고리즘으로 CMD 파일 압축 해제**

즉 CMD 파일은 압축된 상태. 런타임에 해제 후 인터프리트.

STAGE1.CMD를 동일 알고리즘으로 해제 → Shift-JIS 텍스트 341개 블록 확인.

### 3단계 — 스크립트 제어코드 파악

압축 해제된 CMD 파일에서 텍스트 주변 바이트 분석.

| 바이트 | 역할 |
|--------|------|
| `65 00 [SJIS lead]` | 대화 블록 시작 |
| `72 XX` | 줄바꿈 |
| `6b` | 대화 블록 명시 종료 |
| `0f 03` | 아이템 항목 시작 (MESSAGE.CMD) |
| `64 02` | 아이템 설명 줄 구분 |
| `64 XX` (XX≠02) | 아이템 수치 구분 |

핵심 판별 기준: `65 00` 다음 바이트가 Shift-JIS 선행 바이트 범위
(`0x81~0x9F`, `0xE0~0xFC`)인지 여부로 대화/비대화 구분.

## 다른 Compile 타이틀 적용 시 체크리스트

### 압축 알고리즘 동일 여부
- COM 파일 0x100이 `FC 60 8C C8...`으로 시작하면 동일 구조
- `0x113~0x114 = F3 A5` (REP MOVSW) 확인
- Python `decompress()` 함수 그대로 사용 가능

### 제어코드 차이 가능성
같은 개발사라도 타이틀마다 스크립트 포맷이 다를 수 있음.
아래 순서로 재분석:

1. CMD 파일 압축 해제
2. Shift-JIS 텍스트 4자 이상 연속 구간 검색
3. 텍스트 직전/직후 1~4바이트 패턴 집계
4. 자주 등장하는 바이트 = 제어코드 후보

```python
# 제어코드 후보 탐색 예시
from collections import Counter
pre_bytes = Counter()
for i in range(len(data)-1):
    if is_sjis(data, i):
        pre_bytes[data[i-1]] += 1
```

5. 0x65, 0x6b, 0x72 등 동일 코드 쓸 가능성 높음 (같은 엔진이면)
6. 차이가 있으면 새 파서로 분기

### 아이템/메시지 파일 포맷
- `0f 03` 마커는 환세풍광전 고유일 수 있음
- 다른 타이틀에서는 별도 분석 필요
- Shift-JIS 4자 이상 연속 구간 추출 → 번역 가능 여부 판단

## 파서 구조 (상태 머신)

### 대화 파서

```
상태: OUT_OF_DIALOG / IN_DIALOG

IN_DIALOG 진입: 65 00 [SJIS lead]
IN_DIALOG 종료: 6b 또는 다음 65 00

IN_DIALOG 내부:
  72 XX    → 줄바꿈 (cur_text → cur_lines)
  SJIS     → cur_text에 추가
  그 외    → 스킵
```

파일마다 종료 방식이 다름:
- STAGE: `6b` 명시 종료가 기본
- ENDING/MESSAGE: 다음 `65 00 [SJIS]`가 이전 블록을 암묵적으로 종료

두 방식 모두 상태 머신 하나로 처리 가능.

### 아이템 파서

```
상태: name / stat / desc

name 진입: 0f 03
stat 진입: 64 XX (XX != 02)
desc 진입: 64 02

구분:
  72 01    → 줄바꿈 (현재 상태 유지)
  65 00    → 아이템 종료
  0f 03    → 다음 아이템 시작
```

## 재삽입 시 주의사항 (미구현, 다음 단계)

1. **텍스트 길이**: 한글은 2바이트 고정폭이라 일본어와 동일.
   단, 번역 후 글자 수가 늘어나면 줄바꿈 위치 재조정 필요.

2. **오프셋 테이블**: CMD 파일 헤더에 오프셋이 있을 경우
   텍스트 크기 변경 시 재계산 필요. 환세풍광전은 런타임 파싱이라
   고정 오프셋 없음 → 재삽입 비교적 자유로움.

3. **재압축**: 동일 LZ 알고리즘으로 재압축.
   압축 효율이 원본보다 낮아도 파일 크기 증가는 허용됨
   (플로피 용량 내에서).

4. **한글 폰트**: PC-98 폰트 시스템은 16×16 비트맵.
   외부 사례 참고 (이미 한글 PC-98 폰트 패치 사례 존재).

## 출력 형식 (translation.json)

스크립트 처리 우선 설계. 번역 후 재삽입 스크립트가 직접 참조.

```json
{
  "dialogs": [
    {
      "file": "STAGE1.CMD",
      "index": 1,
      "lines": [
        {"offset": 18462, "jp": "「あら　いらっしゃい！", "kr": ""},
        {"offset": 18484, "jp": "　今日はどーしたの？",   "kr": ""}
      ]
    }
  ],
  "items": [
    {
      "offset": 96,
      "name": {"offset": 98,  "jp": "鉄の剣",     "kr": ""},
      "stat": {"offset": 106, "jp": "攻撃力＋２０", "kr": ""},
      "desc": [
        {"offset": 120, "jp": "鉄製の長剣",  "kr": ""}
      ]
    }
  ]
}
```

- `offset`: 압축 해제 후 바이트 오프셋. 재삽입 스크립트에서 직접 참조.
- `stat` 키: 수치 없는 아이템(소모품, 열쇠 등)은 키 자체 없음.
- `kr`: 번역 작업 후 채워 넣는 필드.
