# 공통 도구 노트

`tools/` 아래 스크립트들의 사용법과 설계 메모. 타이틀별 역공학 상세(오피코드, 포맷)는
`tools/HUKYOU.md`·`KAITOU.md`·`KITAN.md`·`TORIMONO.md`에 따로 있고, 여기는 그 타이틀들이
공유하는 도구 — 에디터, 파이프라인, 압축/디스크 유틸 — 를 다룬다.

## 로컬 서버

| 용도 | 포트 | 연상 |
|------|------|------|
| 번역 에디터 (`editor.py`) | **8182** | JP(81) → KR(82) |
| 에뮬레이터 (`serve_emulator.py`) | **9801** | PC-9801 |

```bash
python3 tools/editor.py             # 인자 없으면 터미널에서 대상 선택 (번호/이름, q=종료)
python3 tools/editor.py <title>     # 바로 지정 — hukyou | kaitou | torimono | kitan
python3 tools/editor.py dashboard   # 4개 타이틀 빌드/번들/배포 대시보드 (같은 포트, 편집과 동시 실행 불가)

python3 tools/serve_emulator.py               # 에뮬레이터 정적 서빙, → http://localhost:9801
python3 tools/serve_emulator.py --no-open      # 브라우저 자동 실행 끄기
python3 tools/serve_emulator.py --port 1234    # 포트 지정
```

둘 다 같은 패턴으로 브라우저를 자동으로 연다: 서버를 데몬 스레드로 먼저 띄운 뒤 브라우저를
연다. `serve_forever()`를 메인 스레드에서 먼저 돌리면 브라우저가 아직 안 열린 포트로
접속을 시도해 연결 거부를 맞기 때문이다. 포트가 이미 쓰이고 있으면 트레이스백 대신
"이미 떠 있는지 확인하라"는 안내만 내고 종료한다.

`editor.py`를 인자 없이 실행하면 임의의 기본 타이틀을 열지 않고 선택지를 보여준다. 파이프나
CI처럼 tty가 아닌 환경이면 이 선택 UI 대신 사용법만 출력하고 종료해, 입력을 기다리며 멈추는
일이 없다.

## 반각 한글 (halfwidth Korean)

PC-98 게임 화면의 좁은 슬롯(적 이름, 아이템명 일부 등)은 일반 전각 문자 폭이 안 들어가서,
폰트의 반각 카나 영역에 한글 글리프를 새로 그려 넣어 대응했다. 풍광전과 희담에서 썼다.

### 인코딩 마커 `/X`

KR 텍스트에서 슬래시 한 개는 바로 다음 한 글자만 반각으로 표시하라는 마커다. 여러 글자를
반각으로 만들려면 글자마다 슬래시를 붙여야 한다.

```
'/리프레시워터'    → 리만 반각, '프레시워터'는 전각
'/리/프/레/시워터' → 리프레시 4자 반각, '워터' 2자 전각
'/Gold'           → G만 반각, 'old'는 전각으로 자동 변환
'/G/o/l/d'        → 전체 반각
```

이 매핑은 `charmap.json`에 `/리: 85a4`, `/G: 8566` 같은 형식으로 들어 있다. 인서터
(`hukyou_inserter.encode_korean`, `kitan_inserter.encode_korean_kitan`)가 `/X` 시퀀스를
만나면 charmap에서 키를 찾아 있으면 반각 코드로, 없으면 일반 처리로 넘긴다.

ASCII 반각(`0x8540~0x859E`)은 게임 원본 폰트의 ANK 글리프를 그대로 쓸 수 있어서, charmap에
`/0`, `/A`, `/G` … `/z` 형태로 printable 94자 전체가 이미 등록되어 있다.

### 폰트 슬롯

`emulator/bios/font.bmp`의 `0x85XX` 영역은 원래 PC-98 반각 카나 글리프가 있던 자리다.
이 중 JIS row 42(s2 ≥ 0x9F, 94슬롯)를 한글로 덮어써서 썼다. 실제로 쓰는 범위는
`0x85A4~0x85FC`와 `0x8645~0x867E`이고(단일 소스는 `charmap.json`), 그 사이 게임이 실제로
출력하는 코드(`0x8640~0x8644` 등)는 비워 둔다. 영역은 초성별로 가나다순 분할했다(쌍자음은
해당 자음에 통합):

| 초성 | 범위 | 슬롯 | 예시 |
|------|------|------|------|
| ㄱ(+ㄲ) | 0x85A4~0x85AD | 10 | 가, 거, 게, 그, 기 |
| ㄴ | 0x85AE~0x85B5 | 8 | 나, 노, 니, 닌 |
| ㄷ(+ㄸ) | 0x85B6~0x85C1 | 12 | 다, 데, 드, 디, ... |
| ㄹ | 0x85C2~0x85CD | 12 | 라, 레, 리, ... |
| ㅁ | 0x85CE~0x85D7 | 10 | 마, 머, 미, ... |
| ㅂ(+ㅃ) | 0x85D8~0x85E7 | 16 | 바, 베, 보, ... |
| ㅅ(+ㅆ) | 0x85E8~0x85F5 | 14 | 사, 서, 소, 시, ... |
| ㅇ | 0x85F6~0x8651 | 20 | 아, 어, 오, 우, 이, ... |
| ㅈ(+ㅉ) | 0x8652~0x8659 | 8 | 진, 즈, 져 |
| ㅊ | 0x865A~0x865D | 4 | 츠, 치 |
| ㅋ | 0x865E~0x8666 | 9 | 카, 케, 키, ... |
| ㅌ | 0x8667~0x866E | 8 | 타, 테, 토, ... |
| ㅍ | 0x866F~0x8678 | 10 | 파, 포, 푸, ... |
| ㅎ | 0x8679~0x867E | 6 | 헌, 헤, 후 |

영역 안은 가나다순이고 영역 사이엔 여유 슬롯이 있어서, 새 글자는 해당 초성 영역의 빈
슬롯에 추가하면 된다. `0x85` 영역은 원본 반각 카나(`ヲ`, `ァ` 등)를 덮어쓴 것이고, `0x86`
영역(low half)은 원래 잘 안 쓰는 한자/기호류 반각 글리프가 있던 자리라 게임이 텍스트로
쓰지 않는 것을 확인한 뒤 썼다.

> **빈칸이라고 안전한 슬롯은 아니다.** 폰트 셀이 비어 있어도(잉크 없음) 게임이 그 SJIS
> 코드를 실제로 출력하는 경우(스페이스로 쓰는 등)가 있어서, 거기 글리프를 그리면 인게임에
> 깨져 보인다. 실제로 `0x8640`에 '오'를 넣었다가 게임이 그 코드를 쓰고 있어 깨진 걸 발견해
> `0x864f`로 옮긴 적이 있다. 안전한 슬롯은 위 표의 확정 블록 안으로 한정하고, 새 글리프를
> 추가하면 반드시 인게임으로 확인한다.

### 폰트 BMP 좌표 계산

`emulator/bios/font.bmp`는 2048×2048 1bpp 이미지로, 팔레트 0이 잉크(검정), 1이 배경(흰색)이다.
전각·반각 모두 16px 그리드에 정렬되고, 반각은 셀의 왼쪽 8px만 쓴다.

SJIS 코드에서 셀 위치를 구하는 게 픽셀을 거꾸로 뒤지는 것보다 항상 정확하다:

```
c1, c2 = sjis >> 8, sjis & 0xFF
if c1 >= 0xE0: c1 -= 0x40
c1 -= 0x81
if c2 >= 0x80: c2 -= 1
c2 -= 0x40
ku  = c1 * 2 + c2 // 94 + 1
ten = c2 % 94 + 1

col = ku
row = ten + 32
x, y = col * 16, row * 16   # 반각 글리프는 x..x+7
```

예를 들어 `0x864f`(오)는 ku 11 / ten 16 → (col 11, row 48) → 픽셀 (176, 768)이다. charmap의
반각 글리프 전부 이 공식으로 검증됐다. 전각 한글이 cols 16~40(ku 16~40) · rows 33~126(ten
1~94)에 packed 되어 있는 것과 같은 규칙이고, 반각 한글은 ku 9~12라 전각 블록 왼쪽(col<16)에
온다.

폰트를 막 그린 직후 어느 셀인지 헷갈릴 때는 `git show HEAD:emulator/bios/font.bmp`와
작업 트리를 바이트 비교해 바뀐 픽셀 좌표를 `//16`으로 셀 역산하는 방법도 있지만, 이건
사후 확인용 차선책이고 공식 계산이 우선이다.

### 글리프 작업과 적용 절차

8×16 픽셀 중 왼쪽 8픽셀에 한글을 그리고 오른쪽 8픽셀은 비운다. 둥근모꼴 느낌으로 도트를
직접 찍었다. 적용 순서는: ① 적 이름 등 짧은 슬롯 entry에 `enemy` 태그(풍광전 한정) →
② KR을 `/리/프/레/시` 형태로 변환(스크립트로) → ③ 폰트 글리프와 `charmap.json` 갱신 →
④ 인서터 빌드 → FDI 패치 → 번들 재생성.

NP2kai는 텍스트 plane을 dot-by-dot으로 그려서 글자를 굵게 렌더링하는 옵션이 없다. 글자가
두꺼워 보이는 인상은 SDL2 픽셀 보간(`SDL_HINT_RENDER_SCALE_QUALITY=2`)에서 오는 것이라
텍스트만 sharp하게 만들 방법은 따로 없고, 폰트 자체를 더 얇게 그리는 것만이 유일한 대응이다.

## editor.py — 번역 에디터

800px 고정 폭, 다크 테마의 웹 기반 번역 GUI. 타이틀별 편집과, 4개 타이틀을 한 화면에서
빌드/번들/배포하는 대시보드 두 모드로 동작한다(포트는 8182로 같아서 한 번에 하나만 뜬다).

빌드·번들·배포를 실제로 실행하는 로직은 `pipeline.py`에 모아 뒀고 `editor.py`는 그걸 불러다
HTTP 라우팅만 한다 — 편집 화면의 3버튼과 대시보드가 같은 함수를 호출하므로 두 화면의 동작이
갈릴 일이 없다. 상세는 아래 `pipeline.py` 절 참조.

### 단축키

| 키 | 동작 |
|----|------|
| `Ctrl+S` | 저장 |
| `Ctrl+D` | 마지막 편집 행으로 점프 |
| `[` / `]` | 초과(over) 행 이전/다음 |

`Ctrl`만 인식한다(Mac의 `Cmd`는 브라우저 기본 동작에 양보). 키 매칭에 `e.code`를 써서 한글
IME가 켜진 상태에서도 정상 동작한다.

### 멀티 선택과 화자별 검수

행을 클릭해 시작점을 잡고 다른 행을 클릭하면 그 사이가 범위로 선택된다. 선택하면 하단에
개수와 액션 버튼이 뜬다. `JP 복사`/`KR 복사`는 선택 행 텍스트를 개행으로 이어 클립보드에
복사하고, 모드를 태그 지정/화자 지정으로 토글해 한 번에 하나씩 일괄 적용할 수 있다.

화자별 검수는 entries 포맷(쾌도전·포물장)에서만 켜진다. 같은 화자의 대사를 모아 보이는
기능으로, `translation.json`은 건드리지 않고 화면에서 화자를 계산해서 보여주며 수동으로
지정한 것만 `line.speaker`로 저장된다. 자동 귀속 우선순위는 수동 지정 > `char` 태그 >
speaker 엔트리 첫 줄 > 휴리스틱(짧은 비-「 줄 다음에 「로 시작하면 이름줄로 봄) 순이고,
아이템·메뉴·적·시스템·전투·장소·컷씬 태그는 애초에 이 그룹핑에서 빠진다.

화자 없이 「로 시작하는 줄은 새 엔트리가 이어지는 경우(선행 전각공백)가 아니면 현재
화자를 만료시킨다. 이름표 없는 「 블록이 이전 화자 것으로 잘못 묶이는 걸 막기 위해서다.
진짜 이름줄은 자기 「와 같은 엔트리에 있어서(`手下`+`「お頭`) 이 규칙에 영향받지 않는다.
화자 드롭다운으로 한 명만 필터링할 수 있고, 수동 지정은 파서를 다시 돌려도 kr·tag와
함께 보존된다.

### 검색

JP/KR 부분 일치, 완전 일치 토글을 지원한다. 완전 일치로 검색해서 매칭된 행이 여럿이면
같은 KR을 한 번에 채우는 "전체 적용" 옵션이 뜬다.

### 빌드 / 번들 / 배포

상단바의 세 버튼이 파이프라인 각 단계를 맡는다: `빌드`(인서터 실행, `build/`에 패치 파일
생성) → `번들`(`emulator/<title>.data` 재생성, emsdk 필요) → `배포`(`deploy-docs.sh` 실행,
emulator→docs 동기화와 정합 검사). 보통 이 순서대로 쓰고, 결과는 토스트로 뜬다 — 커밋이나
버전은 안 건드린다.

빌드할 때 `lint.py`의 빠른 검사(깨진문자·일관성)가 같이 돌아 토스트에 합산 표시되고,
문제가 있으면 경고색으로 바뀐다. 타이틀 하나만 왕복할 땐 이 3버튼으로 충분하고, 여러 타이틀을
한꺼번에 처리하려면 아래 대시보드를 쓴다.

### 입력 보조 — 시리즈 용어집

빈 KR 칸의 placeholder에 시리즈 다른 타이틀에서 같은 원문이 어떻게 번역됐는지
`번역 (풍/희/쾌)` 형식으로 보여준다. 매칭은 공백·약물·괄호 등을 제거하고 글자만 비교하는
정규화 일치라서(`lint.py`의 `_norm_jp`와 에디터의 `normJp()`가 같은 문자 범위를 써야 함),
현재 타이틀 번역이 있으면 그게 우선이고 없으면 다른 타이틀 걸 제안한다. 새 타이틀을
시작할 때 전투 메뉴·주문·아이템 획득문 같은 시스템 정형구가 자동으로 제안되는 효과가 있다.
빈 KR 칸의 Byte(길이) 칸을 클릭하면 그 제안이 바로 채워진다.

### 대용량 대응

전 행을 DOM에 렌더링하고 가상 스크롤은 없다. 포물장처럼 행 수가 만 단위가 되면
`rowKey→row` 조회가 병목이 되어서, 데이터를 불러온 뒤 `rowIndex` Map을 한 번 구축해
입력·클릭·저장의 행 조회를 O(1)로 만들고, 저장 후 갱신도 바뀐 행만 콕 집어 반영한다. 이
Map 없이 선형 탐색을 했을 땐 저장이 O(N²)가 되어 수 초씩 멈췄다.

### 대시보드 (`dashboard` 모드)

`python3 tools/editor.py dashboard`로 켜면 4개 타이틀의 빌드/번들/배포 상태를 한 화면에서
본다.

각 타이틀은 `translation.json → build/ → emulator/*.data → docs/` 4단계를 거치는데,
대시보드는 이 흐름을 mtime과 파일 비교로 판정해 `미빌드`·`빌드 필요`·`빌드됨` 식 배지로
보여준다. 희담은 데모 디스크(`kitan-demo.fdi`) 유무를 따로 표시하되, 오프닝 미번역 상태에서
없는 게 정상이라 빌드 실패로 취급하지 않는다. 타이틀별 빌드/번들 버튼과 "전체 빌드+번들"이
있고, 후자는 변경된 타이틀만 순서대로 처리하다가 실패하면 그 자리에서 멈춘다(서버가
`HTTPServer` 단일 스레드라 서버 쪽에서 일괄 처리하면 그동안 서버 전체가 막히므로, 배치는
클라이언트가 순차 호출하는 방식으로 짰다). 배포 버튼은 페이지에 하나만 있다 —
`deploy-docs.sh`가 원래 전 타이틀을 한 번에 처리하기 때문이다. 빌드 신선도 경고로 막힐
타이틀이 있으면 미리 표시하고, 필요하면 `-f` 강제 배포도 버튼으로 노출한다. 실행 로그는
인서터·file_packager·deploy의 원문 출력을 접이식 패널에 그대로 남긴다.

커밋 기능은 `translation/`·`emulator`·`docs/` 안의 변경 파일만 보고 메시지 초안을 자동으로
써 준다(수정 가능한 textarea). `tools/`처럼 이 세 디렉토리 밖의 변경은 절대 같이 커밋되지
않도록 스코프를 고정했다. 메시지는 타이틀별로 어느 단계까지 진행됐는지(`번역 작업` <
`빌드 갱신` < `번역 반영 및 배포`) 보고 조합하고, `translation.json`이 바뀐 타이틀은
`git diff`에서 실제로 바뀐 `kr` 줄 수를 세어 붙인다 — 완벽한 문장을 만드는 게 목표가
아니라 손대기 좋은 출발점을 주는 정도로 설계했다. 시리즈 전체가 공유하는 "환세" 접두어는
메시지에서만 뗀다(다른 화면 표시는 원래 이름 그대로).

**작업 중 실제로 걸렸던 것들:**

- 번들 신선도를 처음엔 타이틀별 `build/<t>/` 디스크만 보고 판정했는데, 폰트처럼 모든
  타이틀 번들에 공통으로 들어가는 입력(`emulator/bios/*`)은 빠져 있었다. 그래서 폰트만
  바뀌고 어느 타이틀의 build/도 안 바뀐 경우, 4개 타이틀 `.data`가 전부 구식 폰트를 담은
  채인데도 "번들됨"으로 잘못 표시되는 일이 실제로 있었다. `_bundle_shared_input_paths()`로
  공용 입력도 비교 대상에 넣어 해결했다 — `_repackage_bundle`이 매번 `bios/` 전체를
  통째로 챙겨 패키징하는 것과 대칭을 맞춘 것.
- `version.js`처럼 타이틀에 안 묶이는 공용 파일은 `deploy-docs.sh`가 `cp -r emulator/*`로
  통째 복사하는데도, 타이틀 배지만 보면 이런 배포를 놓친다. 그래서 `<t>.data`/`<t>.js`를
  뺀 나머지 전체를 따로 비교해 어긋난 파일을 보여주는 공용 파일 행을 별도로 뒀다.
- 배치 실행 도중 상태를 다시 그리면(`render()`) 버튼 `disabled`를 직접 켜둔 게 지워지면서
  배치 진행 중에 버튼이 되살아나는 문제가 있었다. 지금은 `busy` 플래그와 `data-off`
  속성을 분리해서, 렌더링이 다시 일어나도 `syncButtons()`가 최종 비활성 여부를 매번
  다시 계산하도록 고쳤다.

## pipeline.py — 빌드/번들/배포 공용 모듈

`editor.py`의 편집 화면 3버튼과 대시보드가 공유하는 순수 함수 모음이다. 전부 `title`
인자를 받고 `{ok, message, output, warnings, ...}` 형태의 dict를 반환하며, 그걸 HTTP
응답으로 바꾸는 건 호출하는 쪽(Handler)의 몫이다.

| 함수 | 역할 |
|------|------|
| `build(title)` | 인서터 실행(`<title>_inserter.py`) + `lint.analyze` 빠른 검사 |
| `bundle(title)` | `build/` 디스크를 `emulator/rom/`에 복사하고 `file_packager`로 `emulator/<title>.data` 재생성. 희담은 데모 인서터를 먼저 실행하되 실패해도 `warnings`로만 남기고 계속 진행 |
| `deploy(force=False)` | `deploy-docs.sh` 실행(`force`면 `-f`) |
| `status()` | `{titles: {t: 4단계 상태 + deploy_blocked}, shared: 공용 파일 동기 여부}` |
| `shared_status()` | 타이틀별 `<t>.data`/`<t>.js`를 뺀 나머지 `emulator/` 전체가 docs와 맞는지 |
| `_bundle_shared_input_paths()` | `emulator/bios/*`(font_jp.bmp 제외) — 모든 타이틀 번들에 공통으로 들어가는 입력. `_repackage_bundle`의 복사 필터와 반드시 같아야 한다 |
| `predict_deploy_block(title)` | `deploy-docs.sh` 0단계(git-clean 스킵 + mtime)를 파이썬으로 재현해, 배포 전에 막힐 타이틀을 미리 알려준다 |
| `_count_changed_kr(rel_path)` | `translation/<t>/translation.json`의 `git diff HEAD`에서 실제로 바뀐 `kr` 줄 수(커밋 메시지 초안용) |
| `commit_status()` | `COMMIT_SCOPE`(`translation/`·`emulator/`·`docs/`) 안의 git 변경 파일과 자동 메시지 초안 |
| `commit(message)` | 위 스코프만 `git add` 후 커밋. 스코프 밖은 절대 add하지 않고, 스테이징할 게 없으면 실패로 응답(빈 커밋 방지) |

타이틀별로 흩어져 있던 함수를 하나로 통합했다기보다는, `_repackage_bundle`이 애초에
`title` 인자를 받고 있었는데 `editor.py`가 HTTP 응답 작성과 실제 로직을 한 메서드에
섞어 놓았던 걸 분리한 쪽에 가깝다.

`bundle()`은 실패 시 `code`(400=빌드 결과 없음, 500=복사·번들 실패)를 같이 반환한다.
편집 화면의 `/api/emulator-update`는 이 값을 받아 `_send_json_error(msg, code)`로 바꿔서
기존 규약(실패는 400/500 + `{message}`, 성공은 200 + `{ok, message}`)을 그대로 지키고,
대시보드 라우트는 `output`·`warnings`까지 담은 dict를 그냥 200으로 넘긴다 — 같은 함수를
쓰지만 호출하는 화면의 기존 계약은 안 건드리는 방식.

파일이 동기화됐는지 보는 `_synced()`는, `cp -r`로 복사했다면 동기 상태일 때 대상 파일의
mtime이 원본보다 항상 같거나 늦다는 점을 이용해 크기와 mtime으로 먼저 거르고, 그래도
판정이 안 되면 그때만 내용을 전수 비교한다. 수 MB짜리 `.data` 파일 4개를 매번 다 읽지
않으려는 최적화다.

## deploy-docs.sh — docs 배포 동기화·검사

`emulator/`를 `docs/`로 복사하고 배포 정합을 검사한다. 커밋이나 버전은 건드리지 않는다.

```bash
./tools/deploy-docs.sh        # 신선도 확인 → 복사 → 정합 검사
./tools/deploy-docs.sh -f     # 빌드 신선도 경고 무시하고 진행
```

0단계는 빌드 신선도 확인이다. `translation/<title>/translation.json`과
`emulator/<title>.data`가 둘 다 커밋된(clean) 타이틀은 일관 상태로 보고 건너뛰고, 작업
중인 타이틀만 mtime을 비교해 json이 번들보다 최신이면 "편집 후 빌드를 안 했다"고 보고
복사 전에 멈춘다(`-f`로 우회 가능). git 상태와 mtime을 같이 보기 때문에 단순히 touch만
해서 내용은 그대로거나 이미 커밋을 끝낸 상태를 오탐하지 않는다. 이어서 1단계 복사, 2단계
docs↔emulator 동일성 확인, 3단계 `<title>.js`의 `remote_package_size`와 `<title>.data`
실제 크기 비교가 이어지고, 하나라도 어긋나면 종료코드 1을 낸다 — CLAUDE.md의 docs 배포
체크리스트를 그대로 코드로 옮긴 것이다. 대시보드의 `배포` 버튼은 이 스크립트를 그대로
호출하고, 배포가 막힐 걸로 예측될 때만 `-f` 옵션도 버튼으로 노출한다.

## compile_lz.py — Compile LZ 압축 / 해제

희담·풍광전의 CMD·OVL·실행 파일에 쓰인 Compile 자체 LZ 알고리즘 구현이다.

포맷은 간단하다: literal run은 헤더(1~127) 뒤에 그 길이만큼 바이트가 오고, back-reference는
헤더(`0x80 | (length-3)`) 뒤에 거리(`dist-1`)가 온다(length 3~130, dist 1~256). 0x00이
종결자다.

`compress()`는 optimal parsing(DP)을 쓴다. `dp[i]`를 `data[i:]`를 압축했을 때 최소 출력
바이트 수로 두고, 각 위치에서 literal run(길이 1~127)과 match(길이 3~130) 중 비용이 더
적은 쪽을 고르는데, literal run의 헤더 오버헤드(런당 1바이트)까지 정확히 비용에 반영한다.
매치 비용은 거리와 무관하게 2바이트로 고정이라서, 각 위치에서 최장 매치 하나와 그 거리만
구하면 길이 3부터 최장까지를 전부 커버할 수 있다 — 거리별로 전부 따로 기록할 필요가
없다. 매치 탐색은 길이가 `max_len`에 닿으면 바로 끊어서, 반복 패턴이 많은 데이터(코드나
0x00 패딩이 섞인 OVL 등)에서 거리 전수 탐색이 데이터에 따라 폭발하는 걸 막는다. 이
최적화로 압축 결과는 greedy보다 더 작으면서 속도는 훨씬 빨라졌다. 무손실 여부는 전
타이틀의 압축 파일을 round-trip 시켜 바이트 단위로 원본과 같은지 확인해서 검증했다.

반각 디코드(`read_sjis_char`)는 `0x85XX`를 PC-98 반각 폰트 영역으로 본다. `XX < 0x9F`는
반각 영숫자/기호라 그대로 `chr`로 바꾸고, `0x9F~0xDE`는 표준 반각 카나(`_HW_KANA`, 64자)다.
`0x85E3~0x85FC`는 탁점·반탁점이 합성된 카나(`ヴ`, `ガ~ポ` 등)인데 이건 JIS X 0201에 없어서
cp932로 디코드하면 U+FFFD가 나온다 — `_HW_DAKUTEN` 매핑을 따로 둬서 처리했고, 이건 게임
고유가 아니라 폰트 BMP 셀을 직접 읽어 확인한 PC-98 공통 배열이다. 실제로 희담 적 이름
`カルニヴェアン`(카르니베안)이 `ヴ` 때문에 U+FFFD로 깨지면서, 파서의 노이즈 필터(U+FFFD
제거)가 엔트리를 통째로 버려 미파싱되는 일이 있었는데, 매핑 테이블을 확장해서 해소했다.
미지의 반각 코드는 원본 일본어 폰트(`emulator/bios/font_jp.bmp`)에서 SJIS→셀 좌표 공식으로
해당 셀을 잘라 눈으로 확인했다(작업본 `font.bmp`는 한글로 덮여 있어 원본 글리프를 볼 수
없다).

희담의 SC*.CMD는 FDI 안 DISK_B 아카이브의 고정 크기 슬롯에 들어가는데, 압축 결과가
슬롯을 넘으면 `patch_fdi`가 그 파일을 건너뛰고 경고를 낸다. 초과 폭이 크지 않으면(수십
바이트) 검수가 진행되면서 KR이 짧아져 자연히 해소되는 경우가 많았고, 그래도 안 들어가면
그 파일의 KR을 직접 줄여야 한다.

## compile_script.py — 공유 스크립트 워커

환세 시리즈 공통 오피코드 스트림 파서다. 디컴프레스된 청크나 CMD를 바이트 스트림으로
워킹해 텍스트를 추출하는데, 희담 `kitan_parser.extract_dialogs`에서 검증한 모델을
일반화한 것으로 쾌도전과 포물장이 쓴다(포물장은 `BASE_SPEC`을 손대지 않고도 동작을
확인했다).

핵심 원칙은 오피코드를 인자 길이만큼 정확히 소비하는 것이다. 그러면 어디가 텍스트고
어디가 제어·인자·그래픽인지 애초에 헷갈릴 일이 없고, 인자 바이트가 우연히 SJIS 쌍처럼
보여도 텍스트로 오인하지 않는다. 그래서 사후 노이즈 필터가 필요 없다 — 찌꺼기가 나온다면
그건 필터로 걸러낼 게 아니라 오피코드 모델이 불완전하다는 신호로 보고 이 파일을 고친다.
(쾌도전 구파서의 노이즈 필터가 진짜 대사 534개를 같이 걸러낸 적이 있어, 이 원칙을
지키게 됐다.)

```python
from compile_script import walk, BASE_SPEC
blocks = walk(decompressed_bytes)            # 기본 스펙
# blocks: [{'type', 'offset', 'lines': [{'offset', 'jp'}]}]
```

타이틀마다 다를 수 있는 부분만 `ScriptSpec`으로 뺐다: 블록을 새로 여는 오피코드
시퀀스(`openers`), 블록 밖에서 본문 시작을 알리는 시퀀스(`markers`), 인자를 통째로
건너뛸 오피코드와 길이(`skip_opcodes`), 줄 구분자(`break_lead`), 캡처할 최소 글자수
(`min_chars` — 1이면 「나 단일 글자까지 전부 캡처), 오프너 없이 2자 이상 SJIS 런이
나오면 텍스트로 암묵 재진입할지(`implicit_text`, 포인터 테이블을 참조하는 대화용).

새 타이틀을 붙일 땐 먼저 `BASE_SPEC` 그대로 `walk()`를 시도해 보고, 안 잡히는 블록이
있으면 그 타이틀의 오프너·마커를 override로 추가한다. 새 오피코드가 보이면
`skip_opcodes`에 인자 길이를 등록한다. 같은 회사 게임이라 대체로 공유되지만 인자 길이가
다를 수 있어서(쾌도전의 `65`는 1바이트 종료자다) 데이터로 검증하며 맞춰 나가야 한다.

gsovl 고정 오프셋 테이블이나 아이템 정의처럼 오피코드 스트림이 아닌 구조는 이 워커의
대상이 아니고, 타이틀별 파서가 따로 처리한다(희담의 gsovl·items 등).

## pc98disk.py — PC-98 디스크 이미지 도구

Editdisk를 대신해 FDI/HDI/IMG 이미지를 CLI에서 생성하고 편집하는 도구다.

지원 포맷:

| 타입 | 설명 | FAT |
|------|------|-----|
| `fdi-2hd` | 2HD 플로피 (77C/2H/8S, 1024B/sec) | FAT12 |
| `hdi-20mb` | HDD 20MB (615C/4H/17S, 512B/sec) | FAT16 |
| `hdi-40mb` | HDD 40MB (615C/8H/17S, 512B/sec) | FAT16 |
| `hdi-80mb` | HDD 80MB (1024C/8H/17S, 512B/sec) | FAT16 |

기존 이미지를 열 때는 Anex86 FDI 헤더가 있는지 자동 감지하고, 헤더 없는 raw FDI도 지원한다.

```bash
# 빈 디스크 생성
python3 tools/pc98disk.py create output.fdi -t fdi-2hd
python3 tools/pc98disk.py create output.hdi -t hdi-40mb

# 파일 목록 / 추가(동명 파일은 자동 교체) / 추출 / 삭제
python3 tools/pc98disk.py ls image.fdi
python3 tools/pc98disk.py add image.fdi ./local_file.dat DEST.DAT
python3 tools/pc98disk.py add image.fdi ./MSG.DAT              # 대상 이름 생략 시 로컬 파일명 사용
python3 tools/pc98disk.py get image.fdi STAGE1.CMD ./out/STAGE1.CMD
python3 tools/pc98disk.py delete image.fdi OLD.DAT
```

라이브러리로 직접 쓸 수도 있다:

```python
from tools.pc98disk import DiskImage

img = DiskImage.create("game.fdi", "fdi-2hd")
img.add_file("DATA.BIN", data_bytes)
img.save()

img = DiskImage.open("game.fdi")
img.add_file("MSG.DAT", new_data)     # 추가 또는 교체
data = img.read_file("STAGE1.CMD")    # 추출
img.delete_file("OLD.DAT")            # 삭제
entries = img.list_files()             # 목록
img.save()
```

부팅 가능한 PC-98 HDD 이미지(섹터0 IPL + 섹터1 파티션 테이블)는 섹터0이 BPB가 아니라서
한동안 non-FAT으로만 처리됐는데, 지금은 `open()`이 파티션 테이블을 스캔해 첫 FAT 파티션을
자동으로 찾고 ls/add/get/delete가 그 파티션 안에서 동작한다(포물장의 `torimono_kr.hdi`가
이 경로를 쓴다). FAT 파라미터는 디스크 전체 CHS가 아니라 파티션 BPB 자체 값(섹터 크기·총
섹터)으로 계산하고, 모든 FAT/디렉토리 오프셋에 파티션 베이스를 더한다 — 읽기 쪽만 하고
쓰기 쪽에서 이 베이스를 빠뜨리면 IPL 뒤 빈 영역에 조용히 기록되어 유실되는 걸 실제로
겪은 뒤 양쪽 다 맞췄다. IPL과 파티션 테이블 영역 자체는 건드리지 않아 부팅 가능 상태를
보존한다.

루트 디렉토리만 지원하고(서브디렉토리 없음), 파일명은 8.3만 지원하며(LFN 없음), non-FAT
이미지는 목록 조회만 가능하고, 파티션 HDI는 첫 FAT 파티션만 대상으로 한다(다중 파티션
미지원).
